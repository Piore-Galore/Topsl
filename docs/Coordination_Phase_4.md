# Phase 4: safe parallel work and combined verification

Implemented on 14 October 2026. These are local coordinator capabilities tested with disposable repositories and deterministic provider processes. Live provider execution, platform acceptance, and enforced independent review remain separate gates.

`ManagedWorkspaces` attaches detached Git worktrees or selected-file snapshot directories to the same logical project. Creation previews capture a committed Git basis plus safe selected file bytes and instruction hashes. Clean input requires a clean source; dirty or non-Git input requires a reviewed snapshot. Every creation/removal approval is bound to its complete plan digest, source revision, executable identity, target identity and expiry. Creation populates the worktree index without checkout filters/hooks, then writes only reviewed bytes. The source checkout is never reset, stashed, committed or changed. Credential paths, caches and ignored output are omitted; excluded tracked files, submodules, conflicted indexes and symlinks block the worktree route. Snapshots provide an explicit non-Git content manifest.

Task workspace records retain their project attribution and encrypted initial inputs. Inactivity includes canonical filesystem leases and active/uncertain attempts. Cleanup captures the current selected bytes and refuses unprotected files, symlinks and uncertain work. Explicit reviewed cleanup can remove an inactive dirty task worktree while retaining encrypted candidate evidence. Failed operations retain their workspace and recorded intent for reconciliation; they are neither automatically replayed nor automatically deleted.

Runtime dispatch now reserves the canonical concrete workspace instead of excluding an entire project. The existing device/inode lease also protects symlink/path aliases and native terminal writers. Inference completion alone does not release a lease or a concurrency slot: observed child exit or explicit reconciled process absence is required. Legacy uncertainty reserves capacity rather than being treated as free work.

`TaskResourceAllocator` reserves distinct loopback ports and provides task-specific temporary directories and database paths outside pinned candidates. Port handoff is explicit; a third-party process must still fail visibly if another process wins the subsequent bind. Verification uses these paths through `TOPSL_TASK_TEMP`, `TOPSL_TASK_DATABASE`, `TOPSL_TASK_PORT` and `TOPSL_TASK_RESOURCE_ID`. Mutable resources are retained separately from the protected candidate. File permissions and worktrees do not create an OS sandbox; network and external process/filesystem isolation are not inferred.

`ParallelSpecialists` creates deterministic specialist tasks with explicit file ownership, runtime/model assignment, known input manifests and pinned shared interface revisions. All workers and the integrator must have distinct approved managed filesystem identities and matching initial content. Before dispatch, mandatory runtime capabilities, interface revisions, executable trust and the shared budget are checked. A full budget queues the requested task without preparing an orphan attempt; the service retries only a previously requested queued dispatch after capacity is available. New interface revisions block downstream work until the input update/restart protocol is used.

Workers submit immutable candidates only after confirmed provider termination. Out-of-scope edits and deletions are rejected. The queue records the author attempt and input basis. Cancellation retains late candidate evidence with a `late-cancelled` disposition and cannot accept it.

Integration previews compare each worker against its recorded baseline and apply its file deltas to a known integration base. Different edits to the same file become explicit conflicts. The user resolves a conflict by choosing a recorded candidate for that file; unresolved conflicts preserve all worker candidates and leave the integration base untouched. Applying a digest-approved plan acquires the integration workspace writer lease and records input candidates and the combined candidate revision. The written manifest is checked against the reviewed plan. Unknown mutation outcomes retain uncertain ownership.

Individual worker checks never establish combined acceptance. All required commands run against pinned combined bytes, with exact executable identity, environment evidence and protected result artifacts. The initial acceptance harness/selected package scripts are frozen through `check-inputs.ts`; an implementer cannot change or delete them to obtain a passing result. Explicit acceptance requires every required combined check and the current combined revision. Supported query/refresh observation compares the live source identity and bytes, invalidates affected verification and clears current acceptance when an external edit is observed. Historical candidate evidence remains intact. This is an observation boundary, not a claim to discover every outside writer.

The coordinator-wide and per-provider defaults are both two active reserved units. Verified bounded native children consume the same budget as visible attempts; unknown native fan-out is reported as unknown and reserves the complete visible budget. Legacy/native-controlled routes are not mislabeled as approved hidden concurrency. The parallel template currently requires an evidence-backed, enforceable `native-fanout-disabled` capability. Installed live adapters remain gated when this cannot be proven. Worktrees, prompts requesting no delegation and renderer assertions do not prove that capability or enforce reviewer independence.

The shared service exposes workspace preview/apply/query, specialist dispatch/submission/cancellation, integration preview/apply, combined check preview/apply, and explicit combined acceptance commands. Native desktop confirmation supplies trusted digests for filesystem, check, integration and acceptance actions; renderer-supplied digests cannot bypass that boundary. Phase 5 owns the corresponding desktop confirmation and presentation controls.

Validation: the focused parallel workspace suite exercises actual fixture child processes in separate worktrees under one project, alias collision, dirty-input review, changed plan/source rejection, worker-pass/combined-fail behavior, explicit conflicts, pinned review stability, unavailable isolation capability, post-acceptance external edits, native fan-out gating, queued capacity, late cancellation, inactive evidence-preserving cleanup, distinct mutable resources and the shared service command boundary. No model, provider billing, deployment, install/update, or real user checkout operation was invoked by these tests. Repository-wide release checks are reported separately by the parent implementation run.
