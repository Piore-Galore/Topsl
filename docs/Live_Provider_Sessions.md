# Live provider sessions

Topsl's automated suites use stand-in providers and never contact a model. [`scripts/live-session.mjs`](../scripts/live-session.mjs) checks real sessions through Topsl's own interface, using each provider's existing sign-in on the machine that runs it: one provider, or Claude Code followed by Codex continuing the same conversation through a context handoff. A terminal can open in one of Topsl's [terminal modes](Provider_Permissions_Plan.md#terminals), and a Codex chat can use any of its four [presets](Provider_Permissions_Plan.md#codex-chats). Each provider gets one short prompt, which counts toward that account's usage. This covers part of remaining gate 2 in [Implementation status](Implementation_Status.md#remaining-gates-and-deliberate-limits); a session check is not a runtime qualification. With `--qualify`, the script instead runs Topsl's Codex [runtime qualification](#codex-runtime-qualification) through the guided setup, which starts up to three model turns. With `--workflow codex-codex`, it runs that qualification and then [one build and one review](#codex-builds--codex-reviews) of a small seeded project in Topsl's **Build and review** workflow, up to five model turns in all.

## Run it

```sh
npm run build
node scripts/live-session.mjs --claude "$(command -v claude)"
node scripts/live-session.mjs --codex "$(command -v codex)"
node scripts/live-session.mjs --claude "$(command -v claude)" --codex "$(command -v codex)"
node scripts/live-session.mjs --qualify --codex "$(command -v codex)"
node scripts/live-session.mjs --workflow codex-codex --codex "$(command -v codex)"
```

`--claude` or `--codex` alone checks that provider. Both together run Claude Code first and then hand its conversation to Codex, as described [below](#both-handoff-from-claude-code-to-codex). `--terminal` with `--codex` alone opens Codex in Topsl's native terminal instead of a chat, as described [below](#codex-native-terminal). `--mode <id>` opens the terminal, Claude Code's or Codex's, in that mode from Topsl's **Terminal mode** menu instead of **Provider default**, by the id in [terminal-modes.ts](../packages/domain/terminal-modes.ts), such as `plan` or `read-only`. The script stops if the menu does not offer it outside **Advanced**, so it never opens a bypass mode. `--preset <id>` sends the Codex chat in that preset instead of **Read-only review**, by the id in [chat-presets.ts](../packages/domain/chat-presets.ts), such as `edit-on-request`. The provider permissions plan's [live check](Provider_Permissions_Plan.md#build-steps) runs these three:

```sh
node scripts/live-session.mjs --claude "$(command -v claude)" --mode plan
node scripts/live-session.mjs --codex "$(command -v codex)" --terminal --mode read-only
node scripts/live-session.mjs --codex "$(command -v codex)" --preset edit-on-request
```

`--qualify` with `--codex` alone runs the runtime qualification instead of a prompt. Like the qualification itself, it runs on macOS and Linux only. So does `--workflow codex-codex` with `--codex` alone, which runs the qualification and then the [workflow](#codex-builds--codex-reviews). It is the first live run in the [Claude workflows plan](Claude_Workflows_Plan.md#live-runs); the teams with Claude follow once Topsl can run a Claude step. `--model <id>` chooses the Codex model instead of the one Codex reports as default, and must be one Codex reports. `--output <folder>` changes where the evidence goes, and `--keep-profile` keeps the disposable Topsl profile after a pass. Linux needs a display, for example `xvfb-run --auto-servernum`.

## What a run does

- Topsl runs from this checkout with a new `topsl-test-live-*` profile in the operating system's temporary folder, so the user's own Topsl profile is never opened. Packaged builds ignore this test profile switch.
- The billing variables Topsl refuses (`billingConflicts` in [`packages/platform/system.ts`](../packages/platform/system.ts), such as `ANTHROPIC_API_KEY` or `OPENAI_BASE_URL`) are removed from Topsl's environment, as a launch from the Dock would not have them. The report lists the removed names only.
- Native dialogs are answered by the script. It approves only the dialogs listed below, for the exact executable and folder it selected, cancels any other, and records every dialog in the report.
- Each executable is chosen with **Locate runtime** (`select-runtime`) and trusted, and a new empty `live-project` folder inside the profile is added and trusted as a project. With `--workflow`, the seeded project is added instead.
- The prompt is `What is A + B? Reply with only the number.`, with random four-digit numbers whose sum is not already on screen. After a handoff, Codex is asked `Add C to the number Claude Code replied with in the handoff above. Reply with only the number.` A step passes only if the expected sum comes back as a whole number, not inside a longer one.
- With `--qualify`, Topsl also gets `TOPSL_TEST_QUALIFICATION_DIR`: a new `topsl-qualify-*` folder in `~/Library/Caches` on macOS or `~/.cache` on Linux, because a qualification in the temporary folder could not be judged. The script deletes that folder after every run, passed or failed.
- With `--workflow`, the qualification folder is made the same way, and the seeded project goes into a new `topsl-live-*` folder in the same cache folder. It sits outside the temporary folders, as a user's project would, because Codex's workspace-write sandbox lets a turn write there whatever folder it runs in. The script deletes it after every run, passed or failed.
- `report.json` and screenshots go to `test-results/live-session/<claude|codex|codex-terminal|both|qualify|workflow-codex-codex>-<time>/`. A one-provider report keeps that provider's `executable`, `prompt`, `expectedReply`, `replyObserved`, `replySeconds` and `session` at the top level. A report for both keeps them per provider under `steps`, with `conversation` for the shared conversation. The profile is deleted after a pass and kept after a failure.

Approved dialogs: **Which runtime are you locating?** (Claude Code or Codex CLI), **Choose the native executable**, **Allow this native executable?**, **Select a trusted project**, **Trust this project?**, **Connect the experimental Codex integration?** (Codex only), for Claude, the transcript chosen for **Import Claude JSONL**, and, after a handoff is attached, **Send the reviewed context to Codex?** for the one message the script sends. With `--qualify`, **Qualify this Codex runtime with live model turns?** is approved once, and only when its text names the selected executable, the chosen model, up to 3 model turns and the script's qualification folder. With `--workflow`, that dialog is approved the same way, and then two more, each once: **Approve captured inputs and start?**, only when its text names the workflow the script captured, the seeded project's folder, and Codex with the selected runtime and model as both builder and reviewer; and **Run this required check?**, only when its text names the check's executable and arguments and the build that was reviewed.

### Claude Code: native terminal

Topsl runs Claude Code only in its native terminal. Production builds refuse the structured `claude --print` route ([`claudeStructuredGate`](../packages/providers/claude.ts)), so that route is not checked.

| Step | Passes when |
|---|---|
| **Native terminal** in the disposable folder | The mode `--mode` names is chosen in **Terminal mode**, or **Provider default**. Claude Code starts with that mode's arguments (none for **Provider default**), under its own login, model and settings |
| Claude Code's folder trust prompt | **Yes, I trust this folder** is selected and confirmed. Claude Code 2.1.183 selects it first, but 2.1.300 lists and selects **No, exit** first. The script reads the selected answer from the screen, moves to **Yes** with the arrow keys and presses Enter only once the screen shows it selected. The report's `folderTrustDefault` keeps the answer Claude Code had selected |
| Other startup questions | Claude Code asks none. A question about its default permission mode, which Claude Code 2.1.300 asked in two live runs in **Plan**, stops the run before the prompt in every mode: the script answers none of Claude Code's questions except folder trust, because Claude Code saves the answer in its own settings. The report's `startupQuestion` names the question. To go on, answer it in Claude Code itself, outside Topsl, with either answer; on the owner's Mac, it did not come back after that |
| Permission mode | In **Plan**, **Accept edits** or **Auto**, Claude Code shows `plan mode on`, `accept edits on` or `auto mode on` below its input, in place of the shortcuts hint. If it shows anything else, the run stops before the prompt. The other modes are not checked on screen |
| One prompt | Sent once Topsl's terminal screen shows Claude Code's shortcuts hint, or its permission mode in place of the hint, below the input. The output does not count, because it still holds that line after a question has replaced it on the screen. The sum appears in the terminal. A sign-in screen stops the run before any prompt is sent. After it, a sign-in request or an API error Claude Code has stopped retrying ends the run, and the report's `apiError` keeps that error's status |
| `/exit` | The session exits with code 0, Topsl records the run as `completed` with the chosen mode, no terminal stays open and the process is gone. If `/exit` has not ended it after 30 seconds, the script presses Ctrl+C twice and then uses **Close session**, and the report says which ended it |
| History import | Claude Code's transcript for the folder (matched by its `cwd` under `~/.claude/projects`, or `CLAUDE_CONFIG_DIR`) imports through **History → Import Claude JSONL**, and the imported history has Claude's reply with the sum |

Keys and text reach Claude Code by giving Topsl's terminal the keyboard focus, not by clicking it: when a terminal application turns on mouse reporting, the terminal passes clicks to it. Claude Code's prompts are read from Topsl's terminal screen as well as from its output. In the first live run below, Topsl's terminal showed the folder trust prompt, but the output with escape sequences removed did not contain it, so the run timed out. The likely cause is that Claude Code moves the cursor over blank cells instead of writing spaces, which runs its words together in the output. The report's `folderTrustReadFrom` says whether the output or only the screen showed that prompt.

Claude Code keeps that transcript in its own history; the script does not delete it.

The report's `mode` keeps the mode chosen in the menu (`chosen`), the mode and arguments Topsl recorded on the run (`recorded`, `args`), and the mode Claude Code showed below its input, or `? for shortcuts` (`shown`).

### Codex: native terminal

With `--terminal`, Codex runs in Topsl's native terminal instead of a chat. Topsl does not connect to it, so there is no **Models & account** step, and Codex uses its own model and settings.

| Step | Passes when |
|---|---|
| **Native terminal** in the disposable folder | The mode `--mode` names is chosen in **Terminal mode**, or **Provider default**. Codex starts with that mode's arguments, such as `-s read-only -a on-request` for **Read-only** |
| Startup | Codex shows `Ask Codex to do anything` in its composer, or its hints below it, and no longer says `Waiting for startup`. A sign-in screen stops the run. So does a question Codex asks at startup, whether to trust the folder, to update Codex or to switch to a new model, which the script does not answer, because Codex saves the answer in its own settings or updates itself. Codex 0.163.0's own text has these questions, but whether it asks one in a given run is not established; the report's `startupQuestion` names the one it asked |
| One prompt | The sum appears in the terminal. A sign-in request ends the run |
| Ctrl+C twice | The session exits with code 0, Topsl records the run as `completed` with the chosen mode, no terminal stays open and the process is gone. Codex is not sent `/quit`, which would reach the model as a second prompt if Codex did not know the command. If Ctrl+C has not ended it after 30 seconds, the script uses **Close session** |

The report's `mode` keeps the mode chosen, what Topsl recorded on the run, and the first of `read-only`, `workspace-write` or `full access` that Codex's screen showed once it accepted a prompt (`shown`), if any. Codex keeps the session in its own history; the script does not delete it.

### Codex: structured chat

| Step | Passes when |
|---|---|
| **Models & account** | The connection is approved and Codex reports its models and account. The report keeps only the account type and plan, not the sign-in identity |
| One prompt | Sent from a new chat with the chosen model, in the preset `--preset` names or **Read-only review**. If the note under **Permissions** says the preset is not available for this runtime, the run stops before the prompt. Any approval request is declined and listed. The run ends `completed` and the reply contains the sum. The report counts the usage records Topsl stored |

The report's `preset` keeps the preset's id, its name in the menu and the note under it. Its `run` keeps the approval policy Topsl asked Codex for (`approvalPolicy`), and the approval policy, approvals reviewer and sandbox Codex reported at `thread/start` (`reportedPermissions`), also when Topsl stopped the run because they differ. A run that ended before Codex started its turn, such as one Topsl stopped that way, adds nothing to `modelTurns`.

### Both: handoff from Claude Code to Codex

Claude Code runs as above, up to its history import. Codex then continues the imported conversation instead of a new chat:

| Step | Passes when |
|---|---|
| **Models & account** | As for Codex alone |
| **Prepare handoff** | With Codex selected and Claude Code's imported conversation open, Topsl shows the handoff for review. Its text has Claude Code's reply with the sum, and the script then chooses **Attach to next Codex message**. The report keeps the reviewed snapshot's SHA-256, its length and how many messages it carries |
| One prompt | Sent in **Read-only review**, or the preset `--preset` names, with the handoff attached, once **Send the reviewed context to Codex?** is approved. The run ends `completed` and the reply is Claude Code's number plus the new one, which Codex can only work out from the handed-off context |
| Shared conversation | The imported conversation keeps both replies, attributed to Claude Code and Codex |

If the Claude Code step fails, Codex is not started.

### Codex: runtime qualification

`--qualify` runs the [runtime qualification](../README.md#qualify-a-codex-runtime) from the guided setup, with Codex in both roles. The script sends no prompt of its own; the qualification's probes are the model turns.

| Step | Passes when |
|---|---|
| **Models & account** | As for Codex alone. The model is the one Codex reports as default, or the one `--model` names |
| Guided setup | In **Activity → Create a workflow → 2. Team**, **Codex builds · Codex reviews** is chosen and the runtime is selected for both roles. **Discover builder models** lists the model, and it is chosen for both roles |
| **Qualify builder runtime** | Topsl's dialog is approved as described above, and the script does not retry. Topsl records a qualification with every probe passed, none untested, no error, and at most 3 turns started |
| Readiness | Topsl's readiness query and the guided setup both show the builder and reviewer roles satisfied with this qualification |

The report keeps what Topsl recorded: the suite, the model, the turns started, each probe's capability, outcome and detail, any probe not tested, the approval requests the suite declined, any error, and when the qualification expires. It keeps only the account type and plan, and writes the home folder as `~`. `modelTurns` is the number of turns Topsl reports it started, or `null` if Topsl started the qualification but recorded nothing. A failed run keeps the same record, so a failure shows which probe failed. The `candidate-reader` detail also says how Codex reported each tool call when it completed, including whether the call's content holds the probe's marker but never the content, and which items the turn completed.

A qualification counts only in the profile that ran it, and this one is disposable. A pass does not qualify the user's own Topsl; that takes **Qualify builder runtime** there, with up to three more turns.

### Codex builds · Codex reviews

`--workflow codex-codex` runs the qualification above in the same disposable profile, so both roles are ready, and then Topsl's **Build and review** workflow on a seeded project, with Codex in both roles. The script sends no prompt of its own. The workflow's build and review are its model turns, and at most 5 turns start in all.

| Step | Passes when |
|---|---|
| Seeded project | A new `topsl-live-*` folder holds a git repository with a local dependency archive, a binary logo, a build script and `npm run check`, which requires an order total of 900 cents. Its task, in `TASK.md`, is to apply a ten percent discount in `src/order.mjs` without adding a file. The script adds it and trusts it as the project |
| Qualification | As for `--qualify` |
| Guided setup | Under **1. Goal**, the objective `Apply a ten percent discount to the order total in src/order.mjs.` and four acceptance criteria. Under **3. Environment**, **Locked JavaScript / TypeScript · offline** with **Project check script** `check`. Nothing under **4. Scope**. **Capture coordinated workflow** records the workflow at **ready build** |
| Start | **Approve captured inputs and start** is pressed once, and its dialog is approved as described above. Topsl dispatches the build. When the build's turn ends, Topsl captures the folder as the build and dispatches the review in a fresh, read-only Codex session on its own. The script answers none of the build's requests: each waits on the workflow's card, where the owner presses **Deny** or **Review & allow once** and confirms in Topsl's dialog, and the terminal says when one arrives and by when to answer it. Topsl takes no answer to a request after 15 minutes, so the run stops once one has waited that long |
| Review | Topsl reads the review from the reviewer's last message, the answer its turn ended with, and records it for this build. If it has findings, the workflow waits at **ready repair** and the run ends there, because the script starts no repair |
| Required check | If the review found nothing, the workflow waits at **checking**. The script presses **Review and run checks** and approves the check's dialog as described above. The check passes and the workflow waits at **awaiting acceptance**, where the run ends. The script never presses **Review final acceptance** |

The run fails if the build adds a file. Topsl holds a new file at **ready review** until its exact contents are approved, and the script approves no file, so no review runs. It also fails if the check does not pass, if Topsl stops the workflow anywhere else, or if more than 5 turns started.

The report's `workflow` keeps the seeded project's base commit, source identity and file count, the workflow's id, objective and check, the stages the script saw in order, the stage and detail where it stopped, and `stoppedAt`, which is `acceptance` or `findings`. For each turn it keeps the role, the state, the requested and reported model, whether the turn started, its seconds and its usage records. It also keeps each request Codex made during the workflow, with the title and details its card showed and the owner's answer: `allowed` when they confirmed **Allow once** in Topsl's dialog for it, `denied` when they pressed **Deny**, or `unanswered`. The script looks for waiting requests every 2 seconds, so a request answered before it looked is not listed, though Topsl's confirmation of an allowed one is among the report's dialogs. It keeps the build's revision and changes, any output still waiting for review, the review's summary and findings and whether it reviewed this build, and each check run's state, failure phase, error and the end of its output. When Topsl kept no review, `reviewReply` keeps how many messages the reviewer sent and the last one, which is the one Topsl reads, cut at 4,000 characters. `workflow.json` holds Topsl's whole record of the workflow, with the home folder written as `~`. `modelTurns` adds the workflow's turns to the qualification's.

The seeded project is the Round 2 receipt project in a live variant, whose build prints the receipt instead of writing `output/receipt.json`. A check set up through the guided setup may write nothing in its copy of the build except prepared dependencies and common tool caches: every recipe the setup offers has no writable paths, and no screen adds one ([environments.ts](../packages/workflows/environments.ts)). With the Round 2 build, the check ended in an error in its integrity phase, `Unexpected execution output outside reviewed writable paths: output` ([delivery record](Claude_Workflows_Plan.md#step-1-live-codex-workflow-run-17-october-2026)).

## What a pass does not establish

- Sandbox enforcement, tool approvals or edits. For Codex, [runtime qualification](../README.md#qualify-a-codex-runtime) covers those separately.
- That a provider enforces the terminal mode or chat preset. The sum needs no tool, so no permission is tested. For a terminal, the report shows what Topsl passed and, for Claude Code, the mode it showed below its input. For a chat, it shows what Codex reported it adopted, which Topsl checks against what it asked for.
- Packaged applications, other operating systems or other provider versions than the one run.
- Claude Code's billing mode. Its terminal owns its login and billing, and the report does not read them; the screenshots show whatever Claude Code displays.
- Native sidebar or history refresh in the providers' own applications.
- Moving a native session between providers. The handoff gives Codex the reviewed text in a new turn of its own session; neither provider's own history shows the other's messages.
- The live builder and reviewer workflows of R2-AT-37/38 ([acceptance mapping](Round_2_Phase_6.md#acceptance-traceability)), which pair Codex with Claude Code. The handoff check is one chat, not a reviewed candidate, a qualification builds and reviews nothing, and the workflow run has Codex in both roles.
- For a workflow run, the review's quality, independence between the roles (Codex reviews Codex in a fresh, read-only session, which is not an independent second model), a repair, the owner's acceptance, what an answer to one of Codex's requests did beyond the captured build, or any project but the seeded one.
- For a qualification, the user's own Topsl being qualified, as above, or any Codex release, account, managed policy or host other than the one that ran it.

## Check the procedure without a model

Stand-ins in [`tests/fixtures/live-session`](../tests/fixtures/live-session) imitate the parts of each provider that the script drives, without a network or an account. They run on macOS and Linux:

```sh
npm run build
CLAUDE_CONFIG_DIR="$(mktemp -d)" node scripts/live-session.mjs --claude "$PWD/tests/fixtures/live-session/claude.cjs"
node scripts/live-session.mjs --codex "$PWD/tests/fixtures/live-session/codex.cjs"
CLAUDE_CONFIG_DIR="$(mktemp -d)" node scripts/live-session.mjs --claude "$PWD/tests/fixtures/live-session/claude.cjs" --codex "$PWD/tests/fixtures/live-session/codex.cjs"
```

For the qualification, the stand-in is the suite's own scripted app-server, [`codex-qualify.cjs`](../tests/fixtures/codex-qualify.cjs), which answers each probe as a Codex runtime with a working sandbox would. It runs the write probes' commands in a pretend sandbox, and, as Codex 0.163.0 did in the first live run, it refuses an interrupt sent before the reply streams:

```sh
node scripts/live-session.mjs --qualify --codex "$PWD/tests/fixtures/live-session/codex-qualify.cjs"
```

Topsl gives a runtime only a fixed list of environment variables, so the stand-in's failure modes need a wrapper. This one never calls the reader, and its run fails with `Not passed: candidate-reader.` and the reviewer role blocked:

```sh
standin="$(mktemp -d)/codex-skips-reader"
printf '#!/bin/sh\nFIXTURE_READER=skip exec node "%s" "$@"\n' "$PWD/tests/fixtures/codex-qualify.cjs" > "$standin" && chmod +x "$standin"
node scripts/live-session.mjs --qualify --codex "$standin"
```

The workflow run's stand-in is [`codex-workflow.cjs`](../tests/fixtures/live-session/codex-workflow.cjs), the same scripted app-server, which also builds and reviews. Its build applies the discount in `src/order.mjs`. Its review sends a progress note first, as Codex does, then reads that file in the task input, or through the reader when the input leaves it out, and finds nothing, so the run stops at acceptance:

```sh
node scripts/live-session.mjs --workflow codex-codex --codex "$PWD/tests/fixtures/live-session/codex-workflow.cjs"
```

Through a wrapper, `FIXTURE_REVIEW=finding` makes the review report one finding, and the run passes at the findings with no check run. `FIXTURE_BUILD=twenty` applies twenty percent instead: the review finds nothing, and the run fails with `The review found nothing, but the required check failed in its test phase.` `FIXTURE_BUILD=new-file` also adds `src/discount.mjs`, and the run fails in 4 turns, with no review, with `The build added a file that Topsl holds for an exact-hash review before the review turn: src/discount.mjs (pending). The script approves no file, so no review ran.`:

```sh
standin="$(mktemp -d)/codex-adds-a-file"
printf '#!/bin/sh\nFIXTURE_BUILD=new-file exec node "%s" "$@"\n' "$PWD/tests/fixtures/live-session/codex-workflow.cjs" > "$standin" && chmod +x "$standin"
node scripts/live-session.mjs --workflow codex-codex --codex "$standin"
```

`FIXTURE_BUILD_ASK=1` makes the build ask, as Codex does under the untrusted policy, to run `npm run check` and then to change `src/order.mjs`, which it writes only if Topsl allows the change. Someone has to answer those requests on the workflow's card. For a stand-in run, `TOPSL_LIVE_OWNER_STAND_IN=1` has the script play the owner: it presses **Deny** for each command and **Review & allow once** for each file change, and answers Topsl's dialog with **Allow once**. The terminal then says the script answers each request. The script refuses that variable unless Topsl reports the stand-in's version, which ends in `-fixture`, so it never answers for a live Codex. The run passes at acceptance in 5 turns, with the command `denied` and the change `allowed` in the report:

```sh
standin="$(mktemp -d)/codex-asks-first"
printf '#!/bin/sh\nFIXTURE_BUILD_ASK=1 exec node "%s" "$@"\n' "$PWD/tests/fixtures/live-session/codex-workflow.cjs" > "$standin" && chmod +x "$standin"
TOPSL_LIVE_OWNER_STAND_IN=1 node scripts/live-session.mjs --workflow codex-codex --codex "$standin"
```

After a handoff, the Codex stand-in adds the numbers in the current request to the last Claude reply in the handed-off context, so it answers correctly only if that context reaches it. The Claude stand-in refuses to start without `CLAUDE_CONFIG_DIR`, so it never writes into a real Claude Code profile. To check how a refused request is reported, give it an API error status in that folder; the run then fails with `Claude Code reported API error 403 instead of replying.`:

```sh
config="$(mktemp -d)" && echo 403 > "$config/stand-in-api-error"
CLAUDE_CONFIG_DIR="$config" node scripts/live-session.mjs --claude "$PWD/tests/fixtures/live-session/claude.cjs"
```

The live check's three runs have stand-ins as well. The Claude stand-in shows the mode it was started with below its input, and the chat stand-in reports the permissions it was asked for. For a Codex terminal, the stand-in is [`codex-terminal.cjs`](../tests/fixtures/live-session/codex-terminal.cjs), which waits for startup, answers the sum and quits on Ctrl+C twice. It shows the arguments it was started with, so its report's `shown` is `read-only` from that line:

```sh
CLAUDE_CONFIG_DIR="$(mktemp -d)" node scripts/live-session.mjs --claude "$PWD/tests/fixtures/live-session/claude.cjs" --mode plan
node scripts/live-session.mjs --codex "$PWD/tests/fixtures/live-session/codex-terminal.cjs" --terminal --mode read-only
node scripts/live-session.mjs --codex "$PWD/tests/fixtures/live-session/codex.cjs" --preset edit-on-request
```

A `stand-in-mode` file in `CLAUDE_CONFIG_DIR` makes the Claude stand-in show another mode, as if Claude Code's settings had overridden the one passed. With `default` there, a run in Plan fails before the prompt with `Claude Code showed "? for shortcuts" below its input instead of "plan mode on", so no prompt was sent.`:

```sh
config="$(mktemp -d)" && echo default > "$config/stand-in-mode"
CLAUDE_CONFIG_DIR="$config" node scripts/live-session.mjs --claude "$PWD/tests/fixtures/live-session/claude.cjs" --mode plan
```

A `stand-in-question` file in `CLAUDE_CONFIG_DIR` makes the Claude stand-in ask, once the folder is trusted, whether to make auto mode its default permission mode. As the live run in **Plan** suggests Claude Code does, it first draws its input and the line below it, then replaces them with the question, so that line is in the output but not on the screen. A run in any mode then fails before the prompt with `Claude Code asked whether to change its default permission mode before accepting a prompt. The script answers none of Claude Code's startup questions except folder trust, so no prompt was sent.` The stand-in saves an answer, if it gets one, to `stand-in-question-answer` in that folder, so that file's absence shows the question went unanswered:

```sh
config="$(mktemp -d)" && touch "$config/stand-in-question"
CLAUDE_CONFIG_DIR="$config" node scripts/live-session.mjs --claude "$PWD/tests/fixtures/live-session/claude.cjs" --mode plan
```
