# Topsl

A local desktop workbench for native Codex and Claude tools, with an Applications manager for downloads and approved updates.

This repository now contains a working **personal pilot**, alongside the complete [v2.1 design](docs/Topsl_Design.md) and [design review](docs/Topsl_Design_Review.md). The [implementation and acceptance matrix](docs/Implementation_Status.md) distinguishes implemented behavior, automated evidence, native handoffs, and remaining release gates.

## Run locally

Use Node.js 22.12 or newer (the GitHub workflows use Node.js 24) and a native compiler toolchain if prebuilt dependencies are unavailable.

```sh
npm ci
npm start
```

`npm ci` rebuilds SQLite and the terminal module for Electron. `npm start` compiles the app and opens the desktop window. No provider app is installed, updated, trusted, or authenticated by these commands. The first launch discovers installations and checks eligible release metadata.

History and its search index are encrypted with SQLCipher. The database key uses the OS credential store where it is secure; otherwise Topsl asks for a passphrase of at least 12 characters. Linux's insecure `basic_text` backend is rejected. Keep both the database and `vault.json` when backing up a **closed** Topsl profile; losing the vault key loses access to history. Automatic backup/restore management is a later release gate.

## Use the workbench

Topsl opens **Projects**, or restores your last project and view. Its Navigator’s Atlas interface uses parchment and sailcloth in Paper, deep ocean blue in Night, and a square topsail emblem. Pick a project in the sidebar to open its **Overview**. The project desk contains **Sessions**, **Coordinator**, **Tasks**, **Changes**, **Context**, **History**, and **Synchronization**; **Applications** and **Settings** remain available globally. Below 900px, **Navigation** opens a keyboard-accessible dialog.

1. Open **Applications**. Review the detected executable, then choose **Trust executable** before running it. Use **Locate a runtime** for paths that are not discovered automatically.
2. Add a trusted project folder. Its native instructions, extensions, MCP servers, and hooks remain active in native sessions.
3. Under **Sessions**, open **Native terminal** for either provider. Its **Terminal mode** menu lists the provider's own permission modes; **Provider default** passes nothing and leaves the choice to the provider's settings, and each project remembers the last ordinary mode you chose. Claude Code's **Bypass** and Codex's **Full access** sit under **Advanced** and need your confirmation in Topsl's own dialog every time. Use **Native login** to authenticate through the provider's own CLI. Topsl does not read or broker native OAuth tokens. Terminal output is transient, including login output.
4. For structured Codex chats, choose **Connect / test**, load the native models, create a chat, and choose its **Permissions**: **Read-only review**, or workspace edits that **ask**, **ask when needed** or do **no asking**. Each preset sets Codex's sandbox and approval policy, and the composer says what it lets commands do and who decides. **No asking** is offered only for a runtime whose current qualification passed `workspace-write`; otherwise the composer says why it is unavailable. Before sending the prompt, Topsl checks that Codex reports the approval policy, approvals reviewer and sandbox it asked for, and the run's line shows what Codex reported. This is an explicitly experimental local stdio integration. Unknown native client requests are rejected, and unsupported features remain available in the native terminal. When a workspace chat asks, each approval request from Codex appears as a card that says what it would run or change and what allowing does. **Deny** answers at once; **Review & allow once** first asks for Topsl's own confirmation. Read-only review and **No asking** decline every request without asking. See the [provider permissions plan](docs/Provider_Permissions_Plan.md).
5. Import a selected native JSONL transcript under **History**, then search it or prepare an attributed handoff. A handoff holds up to the newest 30 user and assistant messages, 12,000 characters each and 150,000 in all; when these limits leave anything out it drops the oldest messages first and says what it omitted or shortened, in the snapshot and in the preview. Imported transcripts are reference history; they are never silently resumed or written back into the provider's store.
6. To use a Codex runtime as a coordinated workflow builder, connect it and select a reported model under **Tasks → Create a workflow → Team**, then choose **Qualify builder runtime**. See [Qualify a Codex runtime](#qualify-a-codex-runtime). While a workflow's build runs, each request Codex makes to run a command or change a file waits on the workflow's card, with **Deny** and **Review & allow once** as in a chat, unless auto-accept is on.
7. To stop answering permission requests yourself, choose a level under **Settings → Auto-accept**, and confirm it in Topsl's own dialog. **Sandboxed** runs Codex's edit turns, in chats and workflow builds, with no asking in the workspace sandbox on a runtime whose qualification passed `workspace-write`, and opens terminals for editing in Codex's **Workspace, never ask** and Claude Code's **Sandboxed edits**, which turns on Claude Code's own sandbox. **Everything** lets Topsl allow every request Codex makes during an edit turn, noting each one in the conversation, and opens those terminals in **Full access** and **Bypass**, which Topsl still confirms each time. Reviews stay read-only at every level, and managed settings can override either provider. See [Auto-accept](docs/Provider_Permissions_Plan.md#auto-accept-17-october-2026).
8. **Settings → Claude Code transcripts** lets Topsl take Claude's final reply for a workflow's Claude Code step from that session's transcript instead of your paste, once you confirm it in Topsl's own dialog. Topsl reads only that session's file, and anything it does not recognize falls back to your paste. See the [Claude workflows plan](docs/Claude_Workflows_Plan.md#step-3-transcript-read-17-october-2026).
9. To build or review with Claude Code, pick a team with Claude under **Create a workflow → Team** and a trusted Claude Code installation for each Claude role. Topsl passes Claude Code no model or effort, so its own settings decide, and the role needs no qualification. When the workflow reaches a Claude Code step, its card says what the step needs. **Open in Claude Code** copies the step's instructions and opens Claude Code in a terminal on the card: a build or repair in the project folder, in the mode you pick (**Bypass** only while auto-accept is Everything, confirmed each time), and a review in **Plan** in a read-only copy of the build. Paste the instructions and work in Claude Code as usual. After you exit it, tick **Claude Code has stopped** and hand back Claude's final reply, pasted or, with item 8 on, from the transcript. The card lists each step's sessions and replies, and acceptance says which replies you pasted. With Claude in both roles, Topsl says that Claude reviews Claude in a fresh Claude Code session, which is not an independent second model. See [step 4](docs/Claude_Workflows_Plan.md#step-4-claude-reviews-claude-and-the-screens-17-october-2026).
10. To work with a coordinator team, use the **Coordinator** section of a project's **Overview**. Give a goal in the conversation, for example "Change the value to two; coordinate with Opus and Astra, review with Fable and Sol" or "Use three coordinators; include Opus and Astra. Use five reviewers; include Fable and Sol." Each role can hold any number of members, chosen automatically or pinned, and **Change** opens the role editor, where you add, pin, unpin or remove members, set counts, collaboration, scheduling, execution width and the decision rule. Every required member contributes; members waiting for capacity show as queued. Coordinators agree one plan, workers change their own snapshot copies, the review group reviews the integrated candidate, and you accept it in Topsl's own dialog. A code goal can carry a required check (set it with the message or before implementation starts); after the review group is satisfied you run it against the exact candidate, confirming each run, and acceptance needs its current passing result. When two members change one file differently, you choose one member's version of each such file. Acceptance records your decision; **Apply to project folder** then writes the candidate into the folder after its own confirmation, only when the folder has no uncommitted or untracked changes and still matches the goal's starting point. Nothing is committed. Code goals need a Git project. Claude's structured route stays gated, so Claude members show as unavailable, and until a runtime qualifies bounded native fan-out, members run one at a time. See [Coordinator teams](docs/Coordinator_Teams.md).
11. **Recursive Looping (experimental, off by default).** In the **Coordinator** section, **Run mode** switches between **Single goal** (item 10), **Goal loop** and **Endless**; the first visit to a loop mode offers to turn it on. A Goal loop takes one or more goals ("Make sync reliable, add the missing controls, and ensure restart keeps the teams") and keeps assessing, organizing the team, delegating, verifying, repairing and promoting until every required goal has valid evidence on one accepted checkpoint. An Endless loop keeps finding and verifying worthwhile improvements, follows your priorities, and monitors when nothing is worth doing; it runs until you stop it. The coordinators choose roles, member counts and models for every field you did not lock, and can change them between iterations; each change shows its reason. **Review and start** confirms in Topsl's own dialog what the run may do, once. Work happens in Topsl-owned copies: accepted results advance an internal checkpoint, which you inspect and **Publish to folder…** (confirmed, files listed, nothing committed). **Pause** and **Stop** are always shown; turning the feature off pauses running loops and keeps **Stop** available for them. Required checks can run automatically on each candidate only if you allow it when starting; they run on this computer with your permissions, not in a sandbox. Loops need a Git project and run while Topsl is open. It is implemented and tested with stand-ins only, not with live providers. See [Recursive Looping](docs/Recursive_Looping.md).
12. **Claude Code structured route (off by default).** To let coordinator and loop teams use Claude members that Topsl runs itself, turn on **Settings → Claude Code structured route** and confirm it in Topsl's own dialog. Claude Code then runs unattended (`claude --print`) under your own Claude Code login and counts against your Claude subscription usage; its permission lists are Claude Code's own, not operating-system filesystem isolation. Then, under **Applications**, choose **Connect / test** for the trusted Claude Code CLI and **Qualify Claude runtime** with a model id. See [Qualify a Claude Code runtime](#qualify-a-claude-code-runtime). Build and review keeps its Claude roles as steps you run in the terminal (item 9). On 19 October 2026 a live Claude qualification passed on the owner's Mac with Claude Code 2.1.302 and `claude-opus-5-5`, and one live Goal loop with Claude and Codex coordinators, a Claude implementer and Claude and Codex reviewers completed (see [Implementation status](docs/Implementation_Status.md#claude-structured-route--19-october-2026)); that is one bounded pilot, not general acceptance.

The subscription-only pilot blocks known API billing environment overrides. Structured Codex turns require native ChatGPT authentication. Claude's native terminal owns its login, model choice, billing mode, and permissions, apart from the starting permission mode you choose in Topsl; inspect these in the native UI before submitting work. With the Claude Code structured route on (item 12), Topsl passes each Claude turn its model and permission profile, keeps API keys out of Claude Code's environment, and stops a turn that reports API-key credentials. Multiple isolated provider profiles, optional API accounts, and remote hosts remain separate roadmap items.

### Qualify a Codex runtime

Coordinated workflow roles run only on a runtime that Topsl has qualified for the exact executable, native account/profile, native policy file and host. For Codex the policy file is `config.toml` in its home folder, without the entries Codex adds under `projects` the first time it works in a folder; every other setting in it is part of the record, and managed policy is not. **Qualify builder/reviewer runtime** shows a trusted dialog listing the operations, then runs them through your native ChatGPT sign-in. It starts up to three model turns, which count against your subscription usage.

In a disposable folder inside the Topsl profile, the suite asks a review session for a marker reply, asks a second review session to read a second marker through the reviewer's candidate reader, runs one write in Codex's sandbox under the read-only policy and two under the workspace-write policy (one inside the workspace and one outside it), interrupts a long answer, and checks that the runtime process exits. Topsl captures the second marker's one-file build into an encrypted store of its own before the runtime starts, so the reader probe passes only when Topsl answered a `read_range` call that returned the marker and the reply quotes it. The write probes involve no model: Topsl sends each write to Codex as a command to run in its sandbox (`command/exec`), under the same policy a review or an edit turn gets, and inspects the folder itself afterwards. The read-only write passes only when a control command runs in the same sandbox, the write fails and no file appears. The inside write must land and the outside write must fail. Topsl declines any approval request a turn makes. The interrupt is sent once the long answer starts streaming. The folder is deleted afterwards. Topsl refuses to run the suite in a folder inside the OS temporary directory or `/tmp`, including through another name for the same folder such as the macOS firmlink `/System/Volumes/Data/private/tmp`, because Codex's workspace-write sandbox leaves both writable and the outside write could not be judged there. Development test profiles live in the temporary directory, so qualifying from one needs `TOPSL_TEST_QUALIFICATION_DIR` set to a new `topsl-qualify-*` folder outside it.

The result is recorded for 30 days. Changing the executable, account/profile or a recorded native policy setting invalidates it, and a later run replaces it. Qualifications recorded before 17 October 2026 fingerprinted the whole `config.toml`, so they need one more run. A passing run satisfies the builder (implementer) and reviewer roles. A Codex reviewer reads the captured build through tools that Topsl declares on its fresh, read-only session and answers itself, recording every read. The guided setup's default team is **Codex builds · Codex reviews**, so one qualified Codex runtime can fill both roles. The setup and the workflow's card say that Codex reviews Codex in a fresh, read-only session and that this is not an independent second model. The Claude structured route cannot be qualified, so a Claude role runs as a Claude Code step instead, which needs no qualification (item 9 under [Use the workbench](#use-the-workbench)). See the [Codex workflows plan](docs/Codex_Workflows_Plan.md) and the [Claude workflows plan](docs/Claude_Workflows_Plan.md), approved on 17 October 2026. The suite uses POSIX shell probes and runs on macOS and Linux. Its first live run, with Codex CLI 0.163.0 on macOS on 16 October 2026, failed the read-only, workspace-write and interrupt probes. Both writes that landed had been approved by the suite, so those two probes did not separate the sandbox from the approval ([results](docs/Live_Provider_Sessions.md#results)). The suite then turned approvals off for those two probes and waited for the answer to stream before interrupting ([probe fix](docs/Codex_Workflows_Plan.md#step-6-follow-up-sandbox-and-interrupt-probes-16-october-2026)). Its live rerun passed the interrupt, but the model did not attempt the writes the sandbox should block, so the sandbox was not tested, and its reply left out the reader's marker ([rerun](docs/Codex_Workflows_Plan.md#live-rerun-16-october-2026)). The suite now runs the write probes itself in Codex's sandbox, with no model turn, and gives the reader its own turn ([sandbox checks without the model](docs/Codex_Workflows_Plan.md#step-6-second-follow-up-sandbox-checks-without-the-model-16-october-2026)). Its live run passed both write probes and the interrupt, so Codex's sandbox blocked the writes Topsl ran where the policy forbids them. It failed the reader probe: Codex called the reader and got the marker back, but the reply did not quote it, so a Codex reviewer is still blocked ([live run of the rework](docs/Codex_Workflows_Plan.md#live-run-of-the-rework-16-october-2026)). The reader probe now also records how Codex reported its call, including whether the call's content holds the marker, so another live run can show where the line is lost ([reader diagnostics](docs/Codex_Workflows_Plan.md#reader-diagnostics-16-october-2026)). The live run with those diagnostics passed every probe in 3 turns, so one Codex runtime qualified for both roles in its disposable profile. Across the four live runs, the reply quoted the reader's marker twice ([live run with the reader diagnostics](docs/Codex_Workflows_Plan.md#live-run-with-the-reader-diagnostics-16-october-2026)).

### Qualify a Claude Code runtime

A Claude member runs only while **Settings → Claude Code structured route** is on, and only for the purposes a current Claude qualification of that exact executable, Claude login, Topsl's Claude Code arguments and host observed. **Qualify Claude runtime** shows a trusted dialog, then starts 4 Claude Code turns under your login, each a fresh session, in a disposable folder inside the Topsl profile: a review turn returns a marker (`structured-turn`); a review turn, which Claude Code must report as having no tools, is asked to create a file and must leave the folder unchanged (`read-only`); an edit turn writes one file in the workspace and one outside it, and only the inside file may land, with Claude Code reporting the outside write as denied (`workspace-write`); and a review turn reads a marker through Topsl's candidate reader, which Topsl serves to Claude Code from a local MCP server (`candidate-reader`). `claude auth status --json` must report a claude.ai login, every turn must report no API key source, every Claude Code process must stop, and the sessions must be distinct. Interrupts are not tested.

Claude Code has no model list: the model you name enters Topsl's catalog only when Claude Code reports running that exact model, so qualify the full id Claude Code reports rather than an alias. The result is recorded for 30 days, like Codex's, and a changed executable, account or argument profile needs a new run. Turning the setting off blocks every Claude purpose again without deleting the record.

## Shared local projects

Open **Projects → Enable project discovery** to bring native project folders into one catalog. Topsl refreshes the approved sources on startup and every minute while open; **Refresh projects** checks immediately and **Pause discovery** stops observation. Manually added folders are available in the same catalog immediately.

- Codex desktop saved roots and local-project metadata, Codex CLI configured project paths, and Claude's shared project metadata are read from the selected local provider homes. The native dialog shows the exact source files. Only folder names, paths, source identities, and observation status are retained; native trust is not imported.
- Canonical paths merge references to the same folder, including symlink aliases. Every root of a native multi-folder project appears as a separate folder, with its native project reference retained. Separate folders and worktrees keep separate Topsl identities and histories.
- Trust a discovered folder before running a session. Missing or retargeted folders are shown explicitly; **Relink folder** keeps the existing Topsl project identity and history. Removing a folder from a native list never deletes Topsl history or files.
- **Codex native projects → Enable Codex sync** connects a trusted Codex runtime to its local profile. Trusted Topsl folders are registered through the experimental native project API; native names and order flow back into Topsl's catalog and sidebar. Expand the registered projects to rename or reorder native groups. Multi-folder groups retain all roots. **Sync now** refreshes immediately; **Pause Codex sync** stops this connection independently of metadata discovery.
- **Open folder** launches either CLI in the exact shared directory. On macOS, Codex desktop receives the folder through the existing selected application. Claude Desktop receives a `claude://code/new?folder=…` link and asks for native folder-access confirmation. macOS targets the selected Claude application; other platforms use the system's registered Claude handler. Other Codex desktop platforms retain the native folder-picker handoff.

Codex reports **Registry synced** only after native readback. Its desktop can keep a separate sidebar cache, so this does not certify immediate visible sidebar refresh, pins, sections, or chat mirroring. Claude's native sidebar creation/order API is not verified; its integration supplies folder discovery and native folder links. Native formats can change: unsupported or unreadable sources retain their last observation and display an error. Topsl does not edit raw provider registries, copy files between machines, synchronize cloud projects, or import conversations through folder discovery. The [project synchronization notes](docs/Project_Synchronization.md) describe the supported sources and boundaries.

## Applications

The catalog starts with Codex CLI, the desktop application providing Codex (ChatGPT, with legacy Codex discovery), Claude Code CLI, and Claude Desktop. Application lifecycle code is independent of the conversation adapters.

- **Download** creates a preview, then saves a complete checksum-verified official artifact without executing it. Failed and cancelled transfers can be reviewed and retried from byte zero. No partial installer is opened.
- **Install** uses an official native flow. Supported macOS desktop archives are downloaded, checksum-verified, quarantined, and opened for native placement/publisher verification. Other supported installations open the official setup/store route. Finish the native flow, then **Reconcile**. Opening a page or installer never means “installed.”
- **Update** preserves the selected installation's owner and channel. Supported Homebrew casks get one exact package update, with automatic Homebrew refresh disabled. A bundled Codex runtime updates with its desktop parent. Other owners use an explicitly labeled native route.
- Metadata checks run on startup when due, then at most daily per installation, with failure backoff and manual refresh. Discovery also observes local executable changes every five minutes. Topsl does not change native auto-update settings; unavailable settings are shown as unknown.
- Approved changes wait for affected native sessions to be idle. Topsl never force-closes an application to update it. Approvals expire after 15 minutes, including while waiting. Installation changes require a fresh review.
- Interrupted or uncertain jobs remain recorded and block another mutation of that installation. Reconcile against the actual installed version. If an interrupted native owner cannot establish the approved target, repair/finish through that owner; Topsl does not guess, automatically roll back, or blindly replay it.

Installers remain subject to native OS publisher checks and elevation. macOS, Windows, Linux, architectures, and installation channels have independent support gates. A Topsl build on an OS does not certify every vendor installation route on that OS.

### Usage remaining

The top of **Applications** shows how much of each provider's plan is left, as the runtime itself reports it.

- **Codex:** Topsl reads the signed-in account's limits through Codex's `account/rateLimits/read` when you **Connect / test**, load models or account, or choose **Refresh from Codex**, and merges the `account/rateLimits/updated` notifications Codex sends while a chat or workflow turn runs. No thread or model turn is started for the read. Each window shows the share left (100% minus the share Codex reports used), its reset time, when Topsl observed it and whether it came from a read or a rolling update. Codex reports shares, not token counts. A value older than 15 minutes is marked stale, and a window whose reset time has passed shows as unknown until the next read. Credits and Codex's own "usage not allowed" or "limit reached" states are shown when reported. A failed read is shown beside the older values.
- **Claude:** trust a Claude Code executable in Applications, add and trust a project, select it in **Project for Claude usage**, and choose **Refresh from Claude**. Topsl reads Claude Code's native `/usage` display there and shows session, weekly and model-specific percentages. Open Claude Code in that folder first if it needs native sign-in or folder trust. The read starts a short-lived native session with customizations and tools disabled, sends only `/usage`, and closes the terminal. Topsl hashes the identity returned by `claude auth status --json`, checks it again after the read, and retains only quota fields. Reset labels are shown exactly as Claude displayed them; they are not converted into guessed timestamps. Older values remain visible after a failed refresh and become stale after 15 minutes. This display reader was validated with Claude Code 2.1.302 on macOS; unsupported layouts stay unknown. Topsl does not read credentials or private account endpoints. See [Claude usage evidence](docs/Implementation_Status.md#claude-usage-reading--19-october-2026).
- **Your own budget:** each provider card can hold a token budget you set per day, week (from Monday) or month. It is labelled owner-set, not a provider limit, and counts the known input and output tokens of work Topsl ran or opened in that period. Sessions started outside Topsl are not counted, and Claude Code terminal sessions report no usage to Topsl, so when a counted run reported nothing the remainder is shown as "at most". These values never start, block or stop chats or workflows. A [Recursive Looping](docs/Recursive_Looping.md) run is the exception: it waits before admitting new child work while a provider's owner-set budget is used up or the runtime reports its limit reached, as the 19 October 2026 [test campaign](docs/testing/TEST-REPORT.md) confirmed.

See [design §16.6 and §16.8](docs/Topsl_Design.md#166-subscription-quota-snapshots) and the [implementation record](docs/Implementation_Status.md#usage-remaining--18-october-2026).

## Configuration and context

Topsl follows the computer's light or dark appearance by default. The native window and open terminal repaint with the selected palette, without restarting the terminal. **Settings → Appearance** offers **Paper** (light), **Night** (dark) and **System**, the default; a theme you choose is kept until you change it. Until the vault opens, Topsl follows the computer's appearance.

Settings exposes full native settings/instruction files with before/after previews, source-hash checks, an encrypted backup, and a trusted native approval dialog. JSON and TOML syntax are validated. Active sessions block writes. Topsl reports a written file separately from whether a native runtime loaded it. Symlinked settings require the native editor.

The optional project context connection only searches one approved project's history. Its grant expires when Topsl closes. It has no API for updates, configuration writes, run execution, or approvals. With a locally installed Node.js runtime, configure a native MCP client using:

```sh
node /absolute/path/to/Topsl/dist/cli.cjs mcp /absolute/path/to/grant.json
```

The grant file is created through **Settings → Project context connection**. Keep it private. Topsl does not silently edit a provider's MCP configuration.

## Validate and package

```sh
npm run check          # strict TypeScript, deterministic tests, application compilation
npm run test:desktop   # real Electron UI and encrypted restart in a temporary profile
npm run icons:build    # regenerate native icons from the canonical topsail SVG
npm run package       # personal-pilot package for this OS and architecture
npm run verify:mac-package # macOS: verify the extracted bundle signature and topsail icon
```

The test suite runs with Electron's Node ABI so the same native SQLite and PTY modules are exercised. Desktop tests use synthetic projects/transcripts; no vendor account, paid model turn, or real application installation is involved. `npm run test:desktop` runs the main desktop harness, the Coordinator journey, the Atlas layout/contrast/terminal journey and the Recursive Looping journey, each in its own temporary profile; `npm run test:desktop -- scripts/desktop-coordinator-test.mjs` runs only the Coordinator journey. They use local provider stand-ins. Linux GUI tests need a display, for example `xvfb-run --auto-servernum npm run test:desktop`. The Linux CI smoke process uses Chromium's `--no-sandbox` only for that isolated fixture run; shipped application configuration keeps renderer sandboxing enabled.

For an explicitly selected trusted Codex binary, a separate read-only protocol probe uses an empty temporary native home and submits no model turn:

```sh
node scripts/probe-codex.mjs /absolute/path/to/codex
```

To verify the selected runtime's experimental project API, run the optional native acceptance test. It creates, renames, reorders, and removes only temporary fixture projects in an empty native home, with zero model turns:

```bash
TOPSL_NATIVE_PROJECT_BINARY=/absolute/path/to/codex npm test -- tests/codex-projects-native.test.ts
```

To check that the selected runtime accepts the tools Topsl declares on a review thread, run the optional tool-channel test. In an empty native home it opts into the experimental API, starts one fresh read-only thread with the reviewer's candidate reader tools, and checks that the same tools are refused without the opt-in. It starts no turn, so no model request is made:

```bash
TOPSL_NATIVE_TOOLS_BINARY=/absolute/path/to/codex npm test -- tests/codex-tools-native.test.ts
```

To try real sessions through Topsl's interface with your own sign-in, run the live session check after `npm run build`. From a disposable Topsl profile and folder, it opens Claude Code in Topsl's native terminal, sends one Codex chat, or does both, with Codex continuing Claude Code's conversation through a reviewed handoff. Each provider's one short prompt counts toward that account's usage. `--mode` opens a terminal in one of Topsl's terminal modes, never a bypass mode, `--terminal` opens Codex in the native terminal instead of a chat, and `--preset` sends the Codex chat in another preset. With `--qualify` and Codex alone, it instead runs the [Codex runtime qualification](#qualify-a-codex-runtime) through the guided setup, with Codex in both roles, which starts up to three model turns. `--workflow codex-codex` with Codex alone follows that qualification with one build and one review of a small seeded project in **Build and review**, up to five model turns in all, and stops before acceptance. The script answers none of Codex's requests during the build: each waits for you on the workflow's card, and the report records your answer. Answer each within 15 minutes, after which Topsl takes no answer and the run stops. `--workflow claude-codex` and `codex-claude` with both Claude Code and Codex, and `--workflow claude-claude` with Claude Code alone, run the same workflow with Claude Code as builder, reviewer or both. The script turns on Claude Code transcripts in the disposable profile and runs each Claude Code step from the workflow's card as you would: the build in **Accept edits** and the review in **Plan**, Topsl's instructions pasted once, and Claude's reply taken from the session's transcript. It leaves each of Claude Code's permission prompts for you to answer in Topsl's terminal within 15 minutes, declines offers to approve a plan, and stops at any other question. [Live provider sessions](docs/Live_Provider_Sessions.md) describes what it checks and records the results.

```sh
node scripts/live-session.mjs --claude "$(command -v claude)"
node scripts/live-session.mjs --codex "$(command -v codex)"
node scripts/live-session.mjs --claude "$(command -v claude)" --codex "$(command -v codex)"
node scripts/live-session.mjs --claude "$(command -v claude)" --mode plan
node scripts/live-session.mjs --codex "$(command -v codex)" --terminal --mode read-only
node scripts/live-session.mjs --codex "$(command -v codex)" --preset edit-on-request
node scripts/live-session.mjs --qualify --codex "$(command -v codex)"
node scripts/live-session.mjs --workflow codex-codex --codex "$(command -v codex)"
node scripts/live-session.mjs --workflow claude-codex --claude "$(command -v claude)" --codex "$(command -v codex)"
node scripts/live-session.mjs --workflow codex-claude --claude "$(command -v claude)" --codex "$(command -v codex)"
node scripts/live-session.mjs --workflow claude-claude --claude "$(command -v claude)"
```


The output packages are a macOS ZIP, Windows portable EXE, and Linux AppImage. They are personal-pilot builds without Developer ID signing/notarization or Windows publisher signing. macOS bundles use an ad-hoc signature to seal the finished app, helpers, and native modules. Packaging checks the bundle with Apple's strict signature verifier; both Mac CI jobs also extract the ZIP and verify it before recording checksums or uploading a release. An ad-hoc signature verifies bundle integrity but does not identify the publisher or provide Apple notarization. Native runtime compatibility and production eligibility are separate from compilation.

### macOS reports that Topsl is damaged

The published v0.1.1 Mac ZIPs were built with signing disabled. This leaves an invalid Electron bundle signature, so macOS can report that the app is damaged even when the download matches its SHA-256 checksum. The v0.1.1 assets have not been replaced; v0.1.2 is the first release built with the corrected packaging configuration above. To check a particular archive on macOS, run `npm run verify:mac-package -- /absolute/path/to/Topsl.zip`.

Extract the repaired ZIP before opening Topsl. Because the pilot is not notarized, macOS may still request approval. For your own build or a checksum-verified release you trust, try opening the app, then use **System Settings → Privacy & Security → Open Anyway** if offered. [Apple's guidance for opening apps](https://support.apple.com/en-us/102445) explains this approval. A Mac download that opens without this approval requires a Developer ID signature and Apple notarization.

The canonical icon is `assets/brand/topsl.svg`; PNG, ICNS, and ICO exports are kept under `assets/brand/icons/`. Normal builds use those exports. `npm run icons:build` uses the installed electron-builder converter, which may download its conversion tool on the first run. See the [Atlas delivery and validation record](docs/Navigator_Atlas_UI.md).

## GitHub builds and releases

[Compile Topsl](https://github.com/Piore-Galore/Topsl/actions/workflows/build.yml) checks and packages macOS Apple silicon, macOS Intel, Windows x64, and Linux x64 on standard GitHub-hosted runners. It runs only while the repository is public. Standard public runners are free; larger runners are not. [GitHub runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)

The compile workflow uses read-only repository permissions, pinned actions, bounded job timeouts, and no artifact/cache uploads. Package names, sizes, and checksums appear in the run summary. Its packages are not retained after the runner finishes. [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

[Release Topsl](https://github.com/Piore-Galore/Topsl/actions/workflows/release.yml) runs when a `v<version>` tag matching `package.json` is pushed. It builds and tests all four platforms, uploads each package and SHA-256 checksum directly to a draft GitHub Release, and publishes a personal-pilot prerelease without distribution signing/notarization only after every platform passes and the uploaded checksums are verified. Mac archives must also pass extracted-bundle signature verification. Release jobs have repository-content write permission through the temporary `GITHUB_TOKEN`. They use the same public standard runners and pinned actions, without Actions artifact storage or dependency caches. [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

To release, commit the matching version and `docs/releases/v<version>.md` notes to `main`, then create and push that version tag. For the current pilot:

```sh
git tag -a v0.1.2 -m "Topsl v0.1.2 personal pilot"
git push origin v0.1.2
```

Failed builds leave the release in draft. Rerun failed jobs on the same tag to resume; each platform replaces only its own draft assets. Published releases are never overwritten by this workflow. Use a new version and tag for subsequent releases; do not move an existing release tag. Downloads appear on the [releases page](https://github.com/Piore-Galore/Topsl/releases).
